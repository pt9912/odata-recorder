# SPEC-201 — Abgleich der Kataloge mit dem Handbuch (`make katalog-check`)

**Werkzeug:** `make katalog-check`; das Programm `katalog` (Quelle `tools/katalog/`, eigenes Go-Modul ohne Abhängigkeiten, Stufen `katalog-bin` und `katalog` des `Dockerfile`).
Das Ziel hängt an `GATE_CHECKS`; `make gates` fährt es.

**Festlegung:** Das Ziel hält drei Kataloge gegen das Handbuch (docs/user/benutzerhandbuch.md): die Fehlercodes `ODR-E…`, die Schlüssel der Startkonfiguration und die Kommandos des Binary.
Die Regel ist die Entscheidung des Users zum Handbuch (`SPEC-200` Nr. 1): Jeder Eintrag, den das gebaute Binary dem Anwender zeigt, kommt im Handbuch vor, und das Handbuch nennt keinen, den das Binary nicht zeigt.
Das Ziel liest Dateien, es startet das Binary nicht und prüft keinen Inhalt der Zeilen: Es vergleicht Mengen von Namen.
Es ergänzt `SPEC-200` (Handbuch gegen das gebaute Binary) und hängt nicht von dessen Lauf ab.

1. **Mengen.** Je Katalog vier Mengen von Namen:
   - **C** (Code): die Namen, die der Quelltext des Binary führt (Nr. 3 a, 4 a, 5 a).
   - **K** (Spezifikation): die Namen, die die Spezifikation führt (Nr. 3 b, 4 b); für Kommandos keine.
   - **H** (Pflicht des Handbuchs): die Namen, die das Binary dem Anwender zeigt und die das Handbuch daher trägt. **H ist C ohne die Ausnahmen** (Nr. 3 c); für Schlüssel und Kommandos ist H gleich C (Nr. 4 c, 5 b).
   - **W** (Handbuch): die Namen, die das Handbuch nennt (Nr. 6).

   Die Beziehungen, die ein Befund sind (Nr. 7): jeder Name aus C steht in K (soweit K besteht); jeder Name aus H hat eine Zeile in der Tabelle des Handbuchs; jeder Name aus W steht in H.
   **K ohne C ist kein Befund:** die Spezifikation führt, der Code folgt (Greenfield, `harness/conventions.md`); ein Name, den die Spezifikation schon führt und der Quelltext noch nicht, darf dort stehen (`SERVICE_ODATA_VERSION` in `SPEC-110` Nr. 2 vor seinem Leser).
   Ein Name aus K, der nicht in C steht und im Handbuch genannt wird, ist ein Befund über W (Nr. 7, Art 8).
2. **Aufruf, Ausgabe, Ausgangswert.**
   - **a) Aufruf.** `katalog <Wurzel>`: genau ein nicht leeres Argument, sonst die Zeile `Aufruf: katalog <Wurzel>` auf stderr und Exit 2; nichts wird gelesen. *Wurzel* ist ein Verzeichnis, das die Dateien nach Nr. 10 a trägt.
   - **b) Ausgabe.** Ohne Befund: `katalog: ok` auf stdout, Exit 0. Je Befund eine Zeile `katalog: <Katalog>: <Text>` auf stderr (*Katalog* ist `Fehlercodes`, `Schlüssel` oder `Kommandos`), Exit 1; alle Befunde stehen in der Ausgabe, kein Befund bricht ab. Je Eingabefehler eine Zeile `katalog: Eingabe: <Text>` auf stderr, Exit 2. Ein Eingabefehler schließt jeden Befund aus: bei Exit 2 stehen nur Eingabefehler in der Ausgabe, alle, in der Reihenfolge der Quellen (Nr. 8) und innerhalb der Quelle der des Lesens.
   - **c) Wirkung.** Das Programm liest Dateien unter *Wurzel* und schreibt nur nach stdout und stderr; es legt nichts an und startet nichts.
   - **d) Reihenfolge.** Befunde stehen nach *Katalog* (`Fehlercodes`, `Schlüssel`, `Kommandos`), dann nach der Nummer der Befundart (Nr. 7), dann nach Name in Bytefolge, dann nach Zeile aufsteigend. Gleiche Eingabe gibt gleiche Ausgabe, unabhängig von der Reihenfolge der Zeilen in den Quellen, wo diese Reihenfolge keine Zeilenzahl in einen Befund trägt.
3. **Katalog der Fehlercodes.**
   - **a) C: die Tabelle im Quelltext.** Die Datei src/hexagon/model/fehler.go unter *Wurzel*. Gelesen werden ihre Zeichenketten-Literale (Go-Syntax: Literale in Anführungszeichen und Raw-Strings; Kommentare zählen nicht). Ein Literal, dessen Wert mit `ODR-` beginnt, ist ein Code, wenn der Wert ganz `^ODR-E[0-9]{4}$` trifft (ASCII-Ziffern); sonst ist es Befund *Form* und kein Code. Ein Literal, dessen Wert nicht mit `ODR-` beginnt, ist kein Code (auch nicht, wenn es einen nennt). Ein Code, der mehr als einmal als Literal steht, ist Befund *doppelt* und zählt einmal. Die Datei ohne Code ist Eingabefehler `fehler.go: kein Code gefunden`; Literale `"ODR-…"` in anderen Dateien des Quelltexts sind nicht Teil von C (Nr. 9 b).
   - **b) K: der Katalog der Spezifikation.** Die Datei spec/spezifikation.md unter *Wurzel*, der Abschnitt mit der Überschriftzeile `## 4. Fehler-Codes und Logging-Felder` (genau eine, außerhalb von Zäunen; Zäune wie Nr. 6 a) bis zur nächsten Zeile, die mit `## ` beginnt. Der Abschnitt trägt genau eine Tabelle (Nr. 6 c) mit dem Kopf `ID`, `Code`, `Bedingung`, `Aktion` und mindestens einer Datenzeile. Der Code einer Zeile steht in der zweiten Zelle als genau ein Inline-Code-Span (Backtick, Text ohne Backtick, Backtick, sonst nichts in der Zelle), dessen Text die Form von Nr. 3 a trifft; sonst ist es Befund *Form* an dieser Zeile, und die Zeile gibt keinen Code. Ein Code in zwei Zeilen ist Befund *doppelt*.
   - **c) H und die Ausnahmen.** Die Datei harness/katalog-ausnahmen.txt unter *Wurzel* nennt die Codes, die das Binary dem Anwender nicht zeigt: je Zeile `<Code> | <Grund>`, getrennt am ersten `|`, beide Seiten getrimmt; leere Zeilen (nach dem Trimmen ohne Zeichen) zählen nicht, die leere Datei gilt (keine Ausnahme). Eine Zeile ohne `|` ist Eingabefehler `Ausnahmen Zeile <n>: Zeile ohne Trennstrich`. Ein Code, der die Form von Nr. 3 a verfehlt, ist Befund *Form*; ein leerer Grund Befund *Ausnahme ohne Grund*; ein Code in zwei Zeilen Befund *doppelt*; ein Code, der nicht in C steht, Befund *Ausnahme ohne Code*. **H ist die Menge der Codes aus C, die nicht in den Ausnahmen stehen.**
   - **d) W: die Tabelle des Handbuchs und die Nennungen.** Die Tabelle des Abschnitts `Fehlercodes` (Nr. 6) mit dem Kopf `Code`, `Bedeutung`: der Name einer Zeile ist der Text des Inline-Code-Spans der ersten Zelle (Nr. 6 d). Dazu gilt jede Nennung eines Codes an irgendeiner Stelle des Handbuchs als Element von W, in Prosa, Tabelle, Überschrift und umzäuntem Block: ein Vorkommen von `ODR-E` mit der folgenden Folge ASCII-Ziffern, die ganze Folge; trifft sie nicht die Form von Nr. 3 a (zu kurz, zu lang), ist es Befund *Form* an dieser Zeile. Grund: Die Form ist eindeutig, ein Fehlercode in einem Beispiel oder Satz außerhalb der Tabelle wird so ebenfalls gefangen. Ein Code, der in einem umzäunten Block steht, hat damit keine Zeile in der Tabelle; Pflicht (Nr. 7) bleibt die Zeile.
   - **e) Entscheidung zu H, Grund.** Das Binary zeigt dem Anwender einen Code, wenn ein Pfad des Binary ihn als Antwort des Servers, als Meldung des Starts oder als Feld `error_code` des Protokolls ausgibt. Der Quelltext trägt dazu kein Merkmal: die Spalte *Zielbereich* in fehler.go ist zu grob (`ODR-E7001`, `ODR-E7003` und `ODR-E7009` tragen die Ziele `workspace` und `session`, erreichen den Anwender aber über Record und Replay), und eine Änderung der Tabelle läge in der Hand jeder Welle, die einen Code einführt. Die Ausnahmen stehen darum in einer eigenen Datei, und der **Standard ist die Pflicht**: ein neuer Code in fehler.go ist rot, bis ihn ein Slice im Handbuch führt oder mit Grund in die Ausnahmen setzt. Die Ausnahmen heute sind Klassen mit Grund je Zeile: die Admin-API (`ODR-E2101`, `ODR-E7002`, `ODR-E7004` bis `ODR-E7008`, `ODR-E7010` bis `ODR-E7012`), der Mock (`ODR-E6001` bis `ODR-E6003`, `ODR-E6005`), der Import (`ODR-E6004`, `ODR-E6101`, `ODR-E6102`) und der V2-Dienst (`ODR-E6006`). **`ODR-E7001` steht in H** (Replay mit unbekanntem Workspace, `LH-FA-04.b`), ebenso `ODR-E7003` und `ODR-E7009`; **`ODR-E7007` ist Ausnahme** (nur die Anlage eines Workspace durch die Admin-API). **`ODR-E6007`** steht in fehler.go, sobald der Slice des Lesers von Client-Bodies gemergt ist; er gehört bis zu seinem Dienst in die Ausnahmen, und wer fehler.go um ihn erweitert, trägt die Zeile im selben Commit nach.
4. **Katalog der Schlüssel.**
   - **a) C: die Literale des Ladens.** Die Dateien `konfig*.go` ohne `_test.go` im Verzeichnis src/bootstrap unter *Wurzel* (nicht rekursiv). Gelesen werden ihre Zeichenketten-Literale wie in Nr. 3 a. Ein Literal, dessen Wert `^[A-Z][A-Z0-9_]+$` trifft (mindestens zwei Zeichen), ist ein Name; **ein Name innerhalb des Funktionskörpers `nichtGelieferte` ist kein Schlüssel**, sondern ein abgelehnter Name oder ein Präfix (Menge **N**). C sind die Namen außerhalb davon, jeder einmal; ein Name, der an mehreren Stellen steht, ist kein Befund. Grund: Jeder Leser nennt seinen Schlüssel als Literal (`p.wert`, `p.aufzaehlung`, `p.dauer`, `p.groesse`, `p.liste`, `p.listen`, `p.wahrheitswert`, `p.optionalerWahrheitswert`, `p.upstreamURL`, `p.env[…]`); die Regel liest jede Stelle, nicht eine Liste von Lesern. Ohne Name in C ist die Quelle Eingabefehler `konfig*.go: kein Schlüssel gefunden`.
   - **b) K: die Schlüssel dieser Version.** Die Datei spec/spezifikation.md, der Abschnitt mit der Überschriftzeile, die mit `### SPEC-110 — ` beginnt, bis zur nächsten Zeile mit `### `: die Zeile, die mit `2. **Schlüssel dieser Version.**` beginnt, nennt hinter `Geprüft werden` die Schlüssel als Inline-Code-Spans bis zum Ende der Zeile; jeder Span, dessen Text `^[A-Z][A-Z0-9_]+$` trifft, ist ein Name. K ist der Satz dieser Namen. Fehlt der Abschnitt, die Zeile oder ein Name, ist das Eingabefehler `SPEC-110: Schlüssel fehlen`. Der Satz hinter `Gesetzt (nichtleer) und nicht geliefert sind` ist nicht Teil von K (Nr. 9 c).
   - **c) H, W.** H ist C. Die abgelehnten Namen N stehen nicht in H: das Handbuch führt sie nicht als Schlüssel. W ist die Tabelle des Abschnitts `Einstellungen` (Nr. 6) mit dem Kopf `Schlüssel`, `Bedeutung`, Name je Zeile; Schlüssel außerhalb dieser Tabelle sind nicht in W (Nr. 9 d). Ein Name in W, der ein Name oder ein Präfix aus N ist (ein Name beginnt mit dem Präfix), ist Befund *Handbuch nennt abgelehnt*.
5. **Katalog der Kommandos.**
   - **a) C: die Konstanten des Adapters.** Die Datei src/adapters/driving/cli/cli.go unter *Wurzel*, gelesen als Go-Quelltext: jede Konstante, die ein Literal in Anführungszeichen als Wert trägt, dessen Text `^[a-z]+$` trifft, ist ein Kommando (`start`, `version`). Der Programmname (`odata-recorder`) trägt einen Strich und ist keines. Ein Text, der kein Go ist, ist Eingabefehler `cli.go nicht lesbar`; ohne Kommando `cli.go: kein Kommando gefunden`.
   - **b) K, H, W.** K besteht nicht: die Menge der Kommandos gehört zum Vertrag des Adapters (`SPEC-138` Nr. 2) und wird dort von den Tests des Pakets festgehalten. H ist C. W ist die Tabelle des Abschnitts `Kommandos` mit dem Kopf `Kommando`, `Bedeutung`. Das Binary kennt keine Optionen (`SPEC-138` Kopf, `SPEC-110`); das Format hat keine Spalte dafür, und eine Option führt zu einer Änderung dieses Vertrags. Kein Argument ist keine Zeile: es gibt die Version aus und gehört zu `version`.
6. **Das Handbuch lesen.**
   - **a) Eingabe und Zäune.** Die Datei docs/user/benutzerhandbuch.md unter *Wurzel*; nicht vorhanden oder nicht lesbar wie `SPEC-200` Nr. 2 f und 3 a (`Handbuch fehlt: <Pfad>`, `Handbuch nicht lesbar: <Grund>` mit `kein UTF-8` und `NUL`). Zeilen trennt `\n`, ein `\r` davor gehört nicht zur Zeile. Ein Zaun öffnet eine Zeile aus genau drei Backticks mit Info-Zeichenkette ohne Backtick (ohne Einrückung) und schließt die nächste Zeile aus genau drei Backticks (rechts getrimmt); eine Überschrift, eine Tabellenzeile und ein Span in einem Zaun zählen nicht. Ein Zaun ohne Schluss ist Eingabefehler `Handbuch: Zaun nicht geschlossen (Zeile <n>)`.
   - **b) Abschnitt.** Eine Überschrift ist eine Zeile außerhalb von Zäunen aus ein bis sechs `#`, einem Leerzeichen und dem Text (rechts getrimmt). Der Abschnitt eines Katalogs ist die Überschrift mit genau diesem Text (`Fehlercodes`, `Einstellungen`, `Kommandos`), in jeder Ebene, bis zur nächsten Überschrift derselben oder einer höheren Ebene. Keine solche Überschrift ist Eingabefehler `Handbuch: Abschnitt <Text> fehlt`, mehr als eine `Handbuch: Abschnitt <Text> mehrdeutig`.
   - **c) Tabelle.** Der Abschnitt trägt genau eine Tabelle: eine Folge von Zeilen außerhalb von Zäunen, die je mit `|` beginnen; keine ist Eingabefehler `Handbuch: Tabelle in <Text> fehlt`, mehr als eine `Handbuch: Tabelle in <Text> mehrdeutig`. Zellen trennt `|`, außer `\|`; der Anfangsstrich steht, der Schlussstrich darf fehlen; jede Zelle ist getrimmt. Die erste Zeile ist der Kopf (genau die Zellen des Katalogs, bytegleich, sonst Eingabefehler `Handbuch: Kopf in <Text> weicht ab`), die zweite die Trennzeile (jede Zelle aus `-`, mit einem `:` an einem oder beiden Enden erlaubt, sonst Eingabefehler `Handbuch: Trennzeile in <Text> fehlt`); jede weitere Zeile ist eine Datenzeile mit genau zwei Zellen, sonst Eingabefehler `Handbuch Zeile <n>: <k> Zellen statt 2`. Eine Tabelle ohne Datenzeile ist zulässig: W ist dann leer, und jeder Name aus H fehlt (Befund).
   - **d) Zeile.** Die erste Zelle ist genau ein Inline-Code-Span (Backtick, Text ohne Backtick, Backtick, sonst nichts); sonst Befund *Zelle* an dieser Zeile, und die Zeile gibt keinen Namen. Der Text des Spans ist der Name; er trifft die Form des Katalogs (Nr. 3 a, 4 a, 5 a) oder ist Befund *Form*. Ein Name in zwei Zeilen ist Befund *doppelt*.
7. **Befunde.** Jede Art ist ein Text in der Form `katalog: <Katalog>: <Text>`; *Quelle* ist `fehler.go`, `§4`, `Ausnahmen`, `konfig*.go`, `SPEC-110`, `cli.go` oder `Handbuch`, *n* die Zeile der Quelle (bei mehreren Vorkommen die erste). Die Nummer ist die Reihenfolge nach Nr. 2 d.
   1. *Form:* `Form: <Quelle> Zeile <n>: <x> hat nicht die Form` (*x* der Wert, wie die Quelle ihn trägt, in Go-Schreibweise mit `strconv.Quote`, auf 200 Zeichen gekürzt).
   2. *Zelle:* `Zelle: Handbuch Zeile <n>: erste Zelle ist nicht genau ein Name in Inline-Code`.
   3. *doppelt:* `<Name> doppelt in <Quelle>, erstes Vorkommen Zeile <n>` (einmal je Name und Quelle).
   4. *Name ohne Spezifikation:* `<Name> in <Quelle> (Zeile <n>), nicht in <K>` (*K* ist `§4` bzw. `SPEC-110`; nur für Fehlercodes und Schlüssel).
   5. *Ausnahme ohne Grund:* `Ausnahme <Code> (Zeile <n>) ohne Grund`.
   6. *Ausnahme ohne Code:* `Ausnahme <Code> (Zeile <n>) steht nicht in fehler.go`.
   7. *fehlt:* `<Name> fehlt im Handbuch` (kein Name aus H hat eine Zeile in der Tabelle).
   8. *Handbuch nennt Unbekanntes:* `Handbuch Zeile <n> nennt <Name>, der nicht in <C> steht` (*C* ist `fehler.go`, `konfig*.go`, `cli.go`; nur für ein Element von W, das weder in C noch in N steht).
   9. *Handbuch nennt Ausnahme:* `Handbuch Zeile <n> nennt <Code>, der in den Ausnahmen steht` (nur Fehlercodes).
   10. *Handbuch nennt abgelehnt:* `Handbuch Zeile <n> nennt <Name>, den das Binary ablehnt` (nur Schlüssel, Nr. 4 c).
   Die Beziehungen sind unabhängig: ein Name kann mehrere Befunde tragen, kein Befund unterdrückt einen anderen (ein Code, der in fehler.go steht, in K fehlt und im Handbuch fehlt, gibt Art 4 und Art 7).
   Ein Name in K, der nicht in C steht und im Handbuch genannt wird, ist Art 8, kein Sonderfall.
8. **Eingabefehler.** Die Quellen in dieser Reihenfolge: fehler.go, spezifikation.md, Ausnahmen, konfig*.go, cli.go, Handbuch. Je Quelle `<Datei> fehlt: <Pfad>` (nicht vorhanden wie `SPEC-200` Nr. 2 f), `<Datei> nicht lesbar: <Grund>` (vorhanden, aber nicht zu lesen; ein Zeichenketten-Literal, das nicht endet, oder ein Quelltext, den der Scanner von Go ablehnt, ist `kein Go (Zeile <n>)`), und die Eingabefehler der Nummern 3, 4, 5 und 6. §4 ohne Datenzeile ist `§4: keine Datenzeile`, eine Zeile mit anderer Zellenzahl als vier `§4 Zeile <n>: <k> Zellen statt 4`, ein anderer Kopf `§4: Kopf weicht ab`, keine oder mehr als eine Überschrift oder Tabelle `§4: Überschrift fehlt` bzw. `mehrdeutig`, `§4: Tabelle fehlt` bzw. `mehrdeutig`. Eine Datei, die fehlt, schließt die folgenden Prüfungen derselben Quelle aus; die übrigen Quellen werden gelesen, damit alle Eingabefehler in der Ausgabe stehen.
9. **Ungeprüft und akzeptierte Negative.** Je Punkt Grund und Folge im Betrieb.
   - **a) Inhalt der Zeilen.** Die Bedeutung einer Zeile, ihre Wahrheit und die Klasse eines Fehlers werden nicht geprüft. Grund: Der Abgleich liest Mengen von Namen, kein Urteil über Text. Folge: eine falsche Beschreibung bleibt grün; der Probelauf der Abnahme und der Reviewer lesen sie. Die Wörter, die ein Handbuch nicht tragen darf, hält `SPEC-200` (Nr. 10 bis 12): ein Satz der Zelle, der ein Wort der Mengen trifft, ist dort rot.
   - **b) Literale `ODR-…` außerhalb von fehler.go.** Sie sind nicht Teil von C. Grund: Die Tabelle ist die Quelle des Binary; ein Literal an anderer Stelle nennt einen Code der Tabelle oder keinen gültigen. Folge: ein Literal mit einem Code, den die Tabelle nicht führt, bleibt ungesehen; es erreicht den Anwender als Text mit einem Code, den kein Katalog nennt.
   - **c) Erreichbarkeit und die Ausnahmen.** Dass ein Code in den Ausnahmen steht, ist eine Behauptung der Datei, nicht gemessen am Binary. Folge: macht eine Welle einen Code erreichbar und lässt ihn in den Ausnahmen stehen, bleiben Handbuch und Gate grün, und der Anwender sieht einen Code, den das Handbuch nicht nennt. Die Pflicht der Folgewellen ist die Gegenmaßnahme (Nr. 11); ein Fänger fehlt. Umgekehrt: ein Code in H, den das Binary nie ausgibt, steht im Handbuch als unbelegte Aussage; die Abnahme liest. Die Namen hinter `Gesetzt (nichtleer) und nicht geliefert sind` in `SPEC-110` Nr. 2 und `nichtGelieferte` werden nicht verglichen (Folge: eine Abweichung fängt der Test der Konfiguration, nicht dieses Ziel).
   - **d) Schlüssel und Kommandos außerhalb der Tabellen, andere Schreibweisen.** Ein Schlüssel, ein Kommando oder ein Code in Kleinschreibung (`odr-e2001`) in Prosa wird nicht gelesen (W der Schlüssel und Kommandos ist die Tabelle). Grund: Ein großgeschriebenes Wort der Prosa (`JSON`, `HTTP`, die Make-Variable `VERSION`) ist von einem Schlüssel nicht zu unterscheiden. Folge: ein Schlüssel, den das Binary nicht kennt, in einem Satz bleibt grün; die Abnahme liest.
   - **e) Schlüssel, die der Quelltext nicht als Literal nennt.** Ein Name aus einer Konstante, einer Verkettung oder einem Feld statt einem Literal in anderer Datei als `konfig*.go` ist nicht in C. Grund: Die Regel liest Literale der Dateien, nicht den Aufrufgraphen. Folge: ein solcher Leser bleibt ungesehen, bis ein Test der Konfiguration oder die Abnahme ihn findet.
   - **f) Verdrahtung.** Dass das `Dockerfile` die Stufen `katalog-bin` und `katalog` führt, das Ziel an `GATE_CHECKS` hängt, die Stufe ohne Netz läuft und `.dockerignore` die Dateien nach Nr. 10 durchlässt, fängt kein Fall. Folge: Fehlte die Verdrahtung, bliebe `make gates` grün, ohne dass das Handbuch geprüft würde. Beleg: Der Implementer fährt das Ziel vor der Übergabe auf einem Handbuch ohne eine Zeile aus H und nennt das Rot.
   - **g) Mehrere Tabellen und Spalten.** Ein Abschnitt mit zweiter Tabelle ist Eingabefehler (Nr. 6 c), eine dritte Spalte gibt es nicht. Folge: wer Optionen, Status oder eine Maßnahme je Zeile führen will, ändert diesen Vertrag.
10. **Stufe, Wurzel, Verdrahtung.**
    - **a) Wurzel.** Die Stufe `katalog` stellt unter ihrem Arbeitsverzeichnis genau diese Dateien bereit: src/hexagon/model/fehler.go, spec/spezifikation.md, harness/katalog-ausnahmen.txt, docs/user/benutzerhandbuch.md, dazu für die Kataloge der Schlüssel und Kommandos die Dateien `konfig*.go` ohne Tests aus src/bootstrap und src/adapters/driving/cli/cli.go; sie ruft `katalog <Arbeitsverzeichnis>`.
    - **b) Stufen.** `katalog-bin` baut und prüft das Programm (`gofmt`, `go vet`, `go test`, Bau mit `-trimpath`, jeder `RUN` ohne Netz); `katalog` ist von ihr abgeleitet, kopiert die Dateien nach a und ruft das Programm. Die Stufe `gegenproben` kopiert das Programm aus `katalog-bin`, nicht aus `katalog`: ein rotes Handbuch macht die Gegenproben nicht rot. Das Ziel baut `--target katalog` und taggt nichts.
    - **c) Kontext.** `.dockerignore` ist eine Allowlist; die Stufen brauchen `tools/katalog`, spec/spezifikation.md und harness/katalog-ausnahmen.txt dazu (src und docs/user stehen schon darin).
    - **d) Sensors.** Das Ziel braucht eine Zeile in `harness/README.md` §Sensors (Zellen höchstens 200 Zeichen).
11. **Folge für Folgewellen.** Wer einen Fehlercode, einen Schlüssel oder ein Kommando erreichbar macht, entfernt den Code aus den Ausnahmen und führt ihn im Handbuch im selben Slice; wer einen Code in fehler.go einführt, setzt ihn in dieselbe Datei der Ausnahmen oder führt ihn im Handbuch. Sonst ist das Ziel rot (neuer Code) oder, bei der Erreichbarkeit, still (Nr. 9 c).

**Gegenprobe:** Die Fälle G1 bis G15 fahren `katalog` in Wegwerfverzeichnissen gegen einen Baum, der im Fall verändert wird:
- G1 sauberer Stand (fehler.go, §4, Ausnahmen, Handbuch gleich): Exit 0, `katalog: ok`.
- G2 ein Code in fehler.go, nicht in §4: Exit 1, Art 4.
- G3 ein Code aus H ohne Zeile im Handbuch: Exit 1, Art 7.
- G4 das Handbuch nennt einen Code, der nicht in fehler.go steht: Exit 1, Art 8.
- G5 das Handbuch nennt einen Code aus den Ausnahmen: Exit 1, Art 9.
- G6 eine Ausnahme ohne Grund: Exit 1, Art 5.
- G7 eine Ausnahme, die nicht in fehler.go steht: Exit 1, Art 6.
- G8 ein Code doppelt in fehler.go: Exit 1, Art 3.
- G9 ein Literal `ODR-E123` in fehler.go: Exit 1, Art 1.
- G10 der Abschnitt `Fehlercodes` fehlt im Handbuch: Exit 2.
- G11 fehler.go fehlt: Exit 2.
- G12 ohne Argument: Exit 2, `Aufruf:`.
- G13 ein Code in §4, der nicht in fehler.go steht: Exit 0 (K ohne C ist kein Befund).
- G14 ein Code aus H nur im umzäunten Block des Handbuchs, ohne Zeile: Exit 1, Art 7.
- G15 ein Code aus den Ausnahmen mit Zeile im Handbuch: Exit 1, Art 9.

`SPEC-102` nimmt die Fälle bei der Lieferung unter den dann nächsten Fallnummern auf; die Fälle fangen die Verdrahtung in den Stufen nicht (Nr. 9 f).

**Stand:** Nr. 3 (Fehlercodes) mit den Nr. 1, 2, 6 bis 8 und 10 ist der erste Teil der Lieferung; Nr. 4 und 5 (Schlüssel und Kommandos) folgen als zweiter Teil und sind bis dahin festgelegt, nicht geliefert; ihre Befunde (Art 4, 8 und 10 für Schlüssel, Art 8 für Kommandos) und ihre Fälle der Gegenprobe tragen sie dann.

**Grenze:** Das Ziel belegt, dass jeder Fehlercode des Quelltexts, den das Binary dem Anwender zeigt, im Handbuch eine Zeile hat, dass das Handbuch keinen Code nennt, den der Quelltext nicht führt oder den die Ausnahmen aus dem Handbuch nehmen, und dass der Quelltext keinen Code führt, den die Spezifikation nicht kennt. Es beurteilt weder die Bedeutung noch die Erreichbarkeit eines Codes noch die Vollständigkeit der Ausnahmen (Nr. 9).
